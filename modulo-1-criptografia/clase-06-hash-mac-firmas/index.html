    Clase 6 — Integridad y Autenticidad

    Módulo: Criptografía

    Por qué no alcanza con cifrar?

    Hasta ahora nos enfocamos en confidencialidad: que nadie pueda leer el mensaje. Pero hay dos problemas que el cifrado solo no resuelve:

    Integridad: el mensaje llegó sin modificaciones? Un atacante que intercepta un ciphertext puede modificarlo sin descifrarlo — y el receptor no tiene forma de detectarlo.

    Autenticidad: el mensaje lo envió quien dice haberlo enviado? El cifrado garantiza confidencialidad, pero no autenticidad.

    El ataque de bit-flipping (repaso)

    En la Clase 2 vimos que en CTR mode, si un atacante conoce la posición de un campo en el plaintext (por ejemplo, el monto de una transferencia), puede modificar ese byte en el ciphertext y el receptor descifrará un valor distinto sin saberlo. El mensaje llega cifrado, pero adulterado.

    Conclusión: confidencialidad e integridad son problemas independientes. Necesitan soluciones distintas.

    Funciones Hash

    Una función hash criptográfica toma un input de longitud arbitraria y produce un output de longitud fija llamado digest, hash o huella digital.

    H("Hola mundo")           →  a3b4c2...  (256 bits)
H("Hola mundo.")          →  f7e2a1...  (256 bits)  ← completamente distinto
H(archivo de 10 GB)       →  9d1c3f...  (256 bits)

    Propiedades requeridas

    Resistencia a preimagen: dado un hash h, es computacionalmente inviable encontrar un mensaje x tal que H(x) = h. No se puede "revertir" el hash.

    Resistencia a segunda preimagen: dado un mensaje x1, es computacionalmente inviable encontrar x2 ≠ x1 tal que H(x1) = H(x2). No se puede encontrar otro mensaje con el mismo hash.

    Resistencia a colisiones: es computacionalmente inviable encontrar cualquier par (x1,x2) con x1 ≠ x2 tal que H(x1) = H(x2). Nadie puede fabricar dos mensajes distintos con el mismo hash.

    Efecto avalancha: un cambio mínimo en el input produce un hash completamente distinto. No hay correlación observable entre input y output.

    Por qué hash no es cifrado?

    Un error común es tratar el hash como cifrado. No lo es:

    Hash Cifrado
    Reversible No — función de una vía Sí — con la clave
    Clave No requiere Requiere
    Propósito Verificar integridad Confidencialidad
    Output Tamaño fijo Tamaño del orden del input

    El hash no oculta el contenido del mensaje. Si alguien tiene el mensaje original, puede verificar el hash. Pero no puede reconstruir el mensaje a partir del hash.

    Algoritmos

    MD5 (1992): output de 128 bits. Colisiones encontradas en 2004. No usar para seguridad.

    SHA-1 (1995): output de 160 bits. Colisiones demostradas por Google en 2017 (SHAttered). No usar para seguridad.

    SHA-256 / SHA-3 (familia SHA-2 y SHA-3): output de 256 bits. Estándar actual. Sin colisiones conocidas. SHA-256 es el más usado en la práctica (TLS, Bitcoin, Git).

    BLAKE3: alternativa moderna, más rápida que SHA-256, seguridad comparable.

    MAC — Message Authentication Code

    Un MAC es un tag de autenticación calculado sobre un mensaje usando una clave secreta compartida. Garantiza simultáneamente integridad y autenticidad.

    Tag = MAC(K, X)

    El receptor, que conoce K, recalcula el tag y lo compara con el recibido. Si coinciden, el mensaje es auténtico e íntegro.

    Qué garantiza un MAC?

    • Integridad: cualquier modificación del mensaje cambia el tag.
    • Autenticidad: sólo quien conoce K puede generar un tag válido.
    • No garantiza confidencialidad: el mensaje puede estar en claro.

    Optimización de MAC

    La idea es usar una función Hash para generar el tag.

    Por qué no usar H(K ∥ X) (secret prefix)?

    Una construcción intuitiva sería simplemente hashear la clave concatenada con el mensaje. Pero esta construcción es vulnerable al ataque de length extension: dado H(K ∥ X), un atacante puede calcular H(K ∥ X ∥ X') sin conocer K, para cualquier extensión X'. Esto permite falsificar MACs.

    Las funciones de hash dividen el texto en varios bloques y van comprimiendo uno a uno generando un estado intermedio que se va modificando con cada compresión. El digest resultante es el estado interno final. Esta estructura se denomina Merkle-Damgård.

    Por eso, al tener el estado final del hash, se pueden generar nuevos bloques y concatenarlos al final, generando una nueva MAC.

    Por qué no usar H(X ∥ K) (secret suffix)?

    Otra construcción sería hashear el mensaje con la clave concatenada al final. Pero esta construcción es vulnerable a los ataques que apuntan a la segunda preimagen: un atacante intercepta el mensaje con su MAC (X, H(X ∥ K)). Calcula luego X' cuyo hash es el mismo que X, y reemplaza X por X' (X', H(X ∥ K)).

    HMAC

    HMAC (Hash-based MAC) es la construcción estándar que evita el ataque de length extension y a la segunda preimagen:

    HMAC(K, X) = H( (K ⊕ opad) ∥ H( (K ⊕ ipad) ∥ X ) )

    Donde opad e ipad son constantes fijas de padding. La doble aplicación del hash elimina las vulnerabilidades.

    HMAC-SHA256 es el estándar actual en la práctica: TLS, JWT, APIs REST, SSH.

    Limitación del MAC

    MAC requiere que emisor y receptor compartan una clave secreta previamente. Esto lo hace ideal para comunicación entre dos partes que ya se autenticaron (como en TLS después del handshake), pero no resuelve el problema de autenticación frente a terceros — para eso se necesitan firmas digitales.

    Firmas Digitales

    Una firma digital usa criptografía asimétrica para garantizar autenticidad e integridad de forma verificable por cualquier tercero, sin necesidad de clave compartida.

    Firma: S = Sign(Kpriv, X) (Kpriv = clave privada del firmante) Verificación: Verify(Kpub, X, S) (Kpub = clave pública del firmante)

    Propiedades

    Autenticidad: sólo quien posee la clave privada puede generar una firma válida.

    Integridad: la firma cubre el contenido del mensaje — cualquier modificación invalida la firma.

    No repudio: el firmante no puede negar haber firmado — sólo él tiene la clave privada. A diferencia del MAC, un tercero puede verificar la firma sin haber participado en la comunicación.

    RSA como firma digital

    RSA permite invertir los roles de las claves:

    Firma: S = Xd mod n (Bob firma con su clave privada) Verificación: X = Se mod n (Cualquiera verifica con la clave pública de Bob)

    En la práctica no se firma el mensaje completo (sería lento para mensajes largos). Se firma el hash del mensaje:

    S = (H(X))d mod n

    El verificador calcula H(X) y lo compara con Se mod n.

    DSA y ECDSA

    DSA (Digital Signature Algorithm): estándar del NIST basado en DLP, no en factorización. Sólo sirve para firmas (no para cifrado).

    ECDSA: DSA sobre curvas elípticas. Misma seguridad que DSA con claves mucho más cortas. Es el estándar actual en TLS, Bitcoin, y la mayoría de certificados modernos.

    Hash + MAC + Firma: cuándo usar cada uno?

    Hash MAC Firma digital
    Clave requerida No Sí (simétrica, compartida) Sí (asimétrica, par propio)
    Garantiza integridad Sí (si el hash viaja seguro) Sí Sí
    Garantiza autenticidad No Sí (entre las dos partes) Sí (verificable por terceros)
    No repudio No No Sí
    Velocidad Muy rápido Rápido Lento
    Uso típico Checksums, Git, Bitcoin TLS record layer, JWT, APIs Certificados, contratos, código firmado

    El patrón más común en la práctica

    Cifrado autenticado = confidencialidad + integridad + autenticidad

    AES-GCM = AES-CTR (confidencialidad) + GHASH MAC (integridad/autenticidad)

    Que es exactamente lo que vimos en Clase 3 — GCM combina cifrado e integridad en una sola operación. Ahora entendemos por qué: el tag de GCM es un MAC sobre el ciphertext.

    Key Establishment — Establecimiento de claves

    Las firmas digitales resuelven autenticidad. Los MACs resuelven integridad. Pero queda una pregunta sin responder: cómo dos partes establecen una clave de sesión de forma segura y autenticada?

    Este es el problema de key establishment (establecimiento de claves), y es donde todo lo visto converge.

    El problema de distribución de claves

    Si Alice y Bob quieren usar AES-GCM para comunicarse, necesitan una clave simétrica compartida. Cómo la obtienen sin haberlo acordado de antemano?

    La solución más directa — enviarse la clave por el mismo canal que usarán para comunicarse — es circular: si el canal no es seguro, la clave queda expuesta. Si ya fuera seguro, no necesitarían la clave.

    El problema escala mal en redes grandes

    Imaginate una red de n usuarios que quieren poder comunicarse entre sí en forma privada. Si cada par de usuarios necesita una clave simétrica dedicada, el número total de claves es:

    n × (n-1) / 2

Para n = 1.000 usuarios  →  ~500.000 claves
Para n = 1.000.000       →  ~500.000.000.000 claves

    Esto genera tres problemas concretos:

    Distribución: cómo hacer llegar de forma segura tantas claves a cada usuario?

    Almacenamiento: cada usuario necesita guardar n-1 claves. Para redes grandes, esto es inviable y es un riesgo de seguridad — más claves almacenadas significa más superficie de ataque.

    Revocación: si una clave se compromete o un usuario abandona la red, hay que revocar y redistribuir potencialmente miles de claves. No existe un mecanismo eficiente para hacerlo en un sistema puramente simétrico.

    Claves de sesión (KSES)

    La primera optimización es distinguir dos tipos de claves:

    Clave de largo plazo (KEK — Key Encryption Key): una clave simétrica que dos entidades comparten de forma permanente. No se usa para cifrar datos — sólo se usa para proteger el transporte de las claves de sesión.

    Clave de sesión (KSES — Session Key): una clave simétrica efímera, regenerada para cada comunicación. Cifra los datos reales y se descarta al terminar la sesión.

    Flujo: 1. Alice y Bob tienen una KEK compartida de antemano 2. Alice genera una KSES aleatoria 3. Alice envía E(KEK, KSES) a Bob 4. Bob descifra con KEK → obtiene KSES 5. Alice y Bob cifran la conversación con KSES 6. Al terminar, KSES se descarta

    Ventaja: la KEK se usa raramente, lo que reduce su exposición. La KSES se renueva cada vez, limitando el daño si se compromete.

    Problema que queda: sigue requiriendo que cada par de usuarios tenga una KEK compartida de antemano — el problema de la escala no desaparece.

    Key Distribution Center (KDC)

    La solución simétrica al problema de escala es centralizar la gestión de claves en un Key Distribution Center (KDC): un servidor de confianza centralizado que comparte una KEK única con cada usuario de la red.

    Usuarios: Alice, Bob, Carol, ... KDC comparte: - KEK_A con Alice (sólo Alice y KDC la conocen) - KEK_B con Bob (sólo Bob y KDC la conocen) - KEK_C con Carol (sólo Carol y KDC la conocen) ...

    Número de claves necesarias: solo n claves (una por usuario), en lugar de n(n-1)/2.

    Protocolo de key transport con KDC
    1. Alice quiere comunicarse con Bob 2. Alice solicita al KDC una clave de sesión para hablar con Bob 3. KDC genera KSES aleatoria y envía: E(KEK_A, KSES) → a Alice E(KEK_B, KSES) → a Bob 4. Alice descifra con KEK_A → obtiene KSES 5. Bob descifra con KEK_B → obtiene KSES 6. Alice y Bob cifran su conversación con KSES

    Ventaja principal: n claves en lugar de n(n-1)/2. El almacenamiento y la distribución se vuelven manejables.

    Limitaciones del KDC

    Single point of failure: si el KDC cae, nadie puede establecer nuevas sesiones. Requiere alta disponibilidad y redundancia.

    Single point of trust: el KDC conoce todas las KSES. Comprometer el KDC compromete todas las comunicaciones. Es el blanco más valioso de la red.

    Escalabilidad entre dominios: funciona bien dentro de una organización, pero ¿cómo dos organizaciones con distintos KDC establecen comunicación segura? El modelo no escala a comunicaciones por Internet.

    Sin PFS: si el KDC se compromete, todas las KSES pasadas que distribuyó pueden ser reconstruidas.

    La solución: criptografía asimétrica

    Los problemas del KDC no son fallos de implementación — son limitaciones estructurales de la criptografía simétrica para key establishment.

    El cambio fundamental: con criptografía de clave pública, cada usuario tiene su propio par de claves. No hace falta que el KDC distribuya nada — la clave pública de cada usuario puede estar disponible libremente.

    Problema simétrico (KDC) Solución asimétrica
    n(n-1)/2 claves compartidas n pares de claves (uno por usuario)
    KDC conoce todas las KSES Nadie excepto el destinatario que descifra
    Sin PFS DH efímero garantiza PFS
    No escala entre dominios Las claves públicas se publican libremente
    Revocación difícil Certificados con fecha de expiración y listas de revocación
    Key transport con criptografía asimétrica
    Alice quiere enviar una KSES a Bob: 1. Alice genera KSES aleatoria 2. Alice cifra: C = E(Kpub_Bob, KSES) usando clave pública de Bob 3. Bob descifra: KSES = D(Kpriv_Bob, C) usando su clave privada 4. Sólo Bob puede descifrar — ni siquiera Alice puede recuperar KSES desde C
    Key agreement con DH efímero
    Alice y Bob generan la KSES juntos sin que nadie la envíe: 1. Alice genera a efímero → A = ga mod p 2. Bob genera b efímero → B = gb mod p 3. Intercambian A y B (autenticados con firmas) 4. Ambos derivan KSES = gab mod p 5. Nadie más — ni un KDC — conoció KSES en ningún momento

    La asimetría resuelve el problema de distribución sin necesitar un tercero de confianza para cada sesión. La PKI (que veremos a continuación) resuelve el último problema pendiente: verificar que las claves públicas pertenecen a quien dicen.

    PKI — Infraestructura de Clave Pública

    Las firmas digitales resuelven autenticidad, pero generan un nuevo problema: cómo saber que una clave pública pertenece realmente a quien dice?

    Certificados X.509

    Un certificado digital es un documento que asocia una clave pública con una identidad, y es firmado por una Autoridad Certificadora (CA) de confianza.

    Certificado = { identidad, clave_pública, validez, ... }
              firmado por CA

    El cliente confía en la CA (su clave pública viene preinstalada en el sistema operativo o navegador). Si la CA firma el certificado del servidor, el cliente puede verificar la identidad del servidor.

    Cadena de confianza

    En la práctica hay una jerarquía:

    Root CA  →  Intermediate CA  →  Certificado del servidor

    Los navegadores incluyen ~150 Root CAs de confianza. Cada vez que abrís un sitio HTTPS, tu navegador verifica esta cadena.

    TLS

    La imagen completa de TLS 1.3:

    1. El servidor envía su certificado (firmado por una CA).
    2. El cliente verifica la cadena de confianza — confirma identidad del servidor.
    3. Ambos hacen ECDHE para establecer el secreto de sesión.
    4. Todos los datos se cifran con AES-GCM — confidencialidad + integridad.

    Conceptos clave de esta clase

    • Cifrado ≠ integridad: el cifrado oculta el contenido pero no detecta modificaciones. Son problemas independientes.
    • Hash: función one-way, output de longitud fija. Propiedades: resistencia a preimagen, segunda preimagen, colisiones, efecto avalancha. No es cifrado.
    • MAC: tag de autenticación con clave simétrica compartida. Garantiza integridad + autenticidad. HMAC-SHA256 es el estándar.
    • Firma digital: criptografía asimétrica para autenticidad + integridad verificable por terceros + no repudio. Se firma H(X), no X directamente.
    • No repudio: sólo las firmas digitales lo garantizan. Los MACs no — cualquiera de las dos partes con la clave podría haber generado el tag.
    • Key establishment: cómo dos partes acuerdan una clave de sesión de forma segura y autenticada. DH efímero + firmas = PFS sin vulnerabilidad MITM.
    • PKI y certificados X.509: asocian claves públicas con identidades mediante una CA de confianza. Base de HTTPS.
