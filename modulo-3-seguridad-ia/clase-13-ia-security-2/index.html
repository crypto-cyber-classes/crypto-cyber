    Clase 13 — IA Security pt. 2: Amenazas en desarrollo, runtime y controles generales

    Módulo: Ciberseguridad

    1. Amenazas en tiempo de desarrollo

    El entorno de desarrollo de un sistema de IA introduce activos nuevos y sensibles que no aparecen en el desarrollo de software tradicional: datos de entrenamiento reales, parámetros del modelo, configuración, código. Esto amplía la superficie de ataque de maneras específicas.

    Particularidades del entorno de desarrollo de IA: - Los datos de entrenamiento son datos reales y sensibles, no datos de prueba ficticios - Los parámetros, el código y la configuración son propiedad intelectual crítica - La cadena de suministro incluye elementos nuevos: datos externos, modelos pre-entrenados, componentes de ML - Componentes externos pueden ejecutarse dentro del entorno de desarrollo, con acceso a datos sensibles

    1.1. Model Poisoning (Envenenamiento del modelo)

    El envenenamiento del modelo es cualquier ataque que altera el comportamiento del modelo modificando sus datos de entrenamiento, sus parámetros, o elementos del entorno de desarrollo. El objetivo es que el modelo produzca outputs incorrectos o maliciosos.

    1.1.1. Data poisoning (Envenenamiento de datos)

    El atacante manipula los datos de entrenamiento antes o durante el proceso de entrenamiento. Puede hacerlo directamente (si tiene acceso al dataset) o a través de la cadena de suministro (si los datos provienen de fuentes externas).

    Ejemplo: Hechos falsos publicados en internet que son incorporados al dataset de un LLM durante su entrenamiento, causando que el modelo los reproduzca como verdaderos.

    Controles: - Mayor volumen de datos de entrenamiento para diluir datos maliciosos (more train data) - Control de calidad de datos (data quality control) para intentar detectar datos maliciosos - Distorsión aleatoria de los datos de entrenamiento para reducir la influencia de muestras individuales (train data distortion) - Modelos robustos al envenenamiento (poison robust model)

    1.1.2. Model poisoning en el entorno de desarrollo

    El atacante manipula directamente los parámetros del modelo, el código, la configuración o las librerías dentro del entorno de desarrollo. No necesita tocar los datos de entrenamiento.

    1.1.3. Supply-chain model poisoning

    El atacante compromete un modelo pre-entrenado que la organización va a usar como base. La mayoría de los modelos actuales se obtienen de repositorios externos (open source, APIs de proveedores) y luego se hace fine-tunning. Estos modelos pueden haber sido manipulados en el origen o en tránsito.

    Si el modelo pre-entrenado comprometido se usa para entrenar otro modelo, el ataque se denomina transfer learning attack: el envenenamiento se propaga a través de la cadena de entrenamiento.

    Tipos de manipulación en supply chain: - Envenenamiento de los datos usados para pre-entrenar el modelo - Modificación directa de los parámetros del modelo antes de su distribución

    Control: Gestión de la cadena de suministro de modelos y datos (supply chain manage) — verificar la procedencia e integridad de modelos y datos externos.

    1.2. Filtración de datos sensibles en desarrollo

    A diferencia del software tradicional, donde los entornos de desarrollo usan datos ficticios, el entorno de desarrollo de IA contiene datos reales y sensibles que, si se filtran, pueden causar brechas de confidencialidad significativas.

    1.2.1. Filtración de datos de entrenamiento

    Acceso no autorizado a los datos usados para entrenar el modelo. Puede exponer datos personales, datos sensibles, secretos comerciales, o información confidencial de clientes.

    1.2.2. Filtración de parámetros del modelo (robo en desarrollo)

    Acceso no autorizado a los parámetros del modelo durante el desarrollo. Equivale al robo de propiedad intelectual y permite al atacante construir ataques más sofisticados contra el sistema en producción.

    1.2.3. Filtración de código fuente o configuración

    Acceso no autorizado al código fuente, configuración del modelo o documentación técnica. Expone detalles de implementación que pueden facilitar otros ataques.

    Control general: Seguridad del entorno de desarrollo (dev security) — aplicar controles de seguridad tradicionales (cifrado, control de acceso, monitoreo) a los activos específicos de IA: datos de entrenamiento, parámetros, código y configuración.

    2. Amenazas en runtime

    Las amenazas en runtime son ataques al sistema de IA en operación, por fuera de la inferencia. A diferencia de las amenazas vía uso (que se realizan enviando inputs al modelo), estas son amenazas a la infraestructura que soporta el sistema.

    2.1. Amenazas convencionales de software

    Un sistema de IA es un sistema de software y por lo tanto es vulnerable a cualquier ataque convencional: SQL injection, escalamiento de privilegios, vulnerabilidades en dependencias, ataques a la infraestructura cloud, etc.

    Estos ataques no son específicos de IA, pero cuando afectan a un sistema de IA sus consecuencias pueden ser más graves: un atacante que compromete el software puede modificar parámetros del modelo, alterar datos, o robar inputs sensibles de los usuarios.

    Controles: Los mismos controles de seguridad aplicativa convencional aplicados a los activos específicos de IA.

    2.2. Runtime model poisoning

    El atacante manipula el comportamiento del modelo alterando sus parámetros directamente en el sistema en producción, sin pasar por el proceso de entrenamiento. También incluye la manipulación de la lógica de input/output del modelo funcionando.

    Controles: - Integridad del modelo en runtime: proteger el almacenamiento de parámetros con controles tradicionales (control de acceso, checksums, cifrado) (runtime model integrity) - Integridad de input/output del modelo: proteger la lógica de entrada/salida contra manipulación en tránsito, por ejemplo contra ataques man-in-the-middle (runtime model I/O integrity)

    2.3. Robo del modelo en runtime

    El atacante obtiene los parámetros del modelo directamente desde el sistema en producción, accediendo a ejecutables, memoria u otros medios de almacenamiento o transferencia. El atacante roba los parámetros directamente, sin necesidad de reconstruir el modelo desde cero.

    También incluye side-channel attacks: el atacante no roba el modelo completo, sino que infiere información sobre su estructura o parámetros observando características como tiempos de respuesta o consumo energético durante la inferencia.

    Controles: - Confidencialidad del modelo en runtime: controles de seguridad convencionales sobre el almacenamiento de parámetros (control de acceso, cifrado, Trusted Execution Environments) (runtime model confidentiality) - Ofuscación del modelo (model obfuscation)

    2.4. Manejo incorrecto de outputs

    Las salidas de un modelo de IA pueden contener contenido que, si no se maneja correctamente, ejecuta ataques de inyección tradicionales en los sistemas que consumen esos outputs: SQL injection, XSS, command injection, etc.

    El modelo puede generar este contenido porque fue manipulado para hacerlo (prompt injection), porque alucinó código o comandos, o porque reprodujo contenido malicioso de sus datos de entrenamiento.

    Ejemplo: Un agente de IA genera código SQL como parte de su respuesta. Si ese código se ejecuta directamente sin sanitización, puede contener una inyección SQL.

    Control: Sanitizar los outputs del modelo antes de usarlos en otros sistemas (encode model output).

    2.5. Filtración de datos de input

    Los inputs que los usuarios envían al modelo pueden contener información sensible: preguntas sobre datos confidenciales, documentos internos, secretos de la organización. Si el sistema no protege adecuadamente esos inputs, pueden filtrarse hacia terceros o ser utilizados para entrenar otros modelos sin consentimiento.

    Ejemplo: Un empleado usa un LLM externo para resumir un contrato confidencial. El texto del contrato es enviado al proveedor externo como input y puede ser utilizado para entrenar su modelo.

    Control: Confidencialidad del input del modelo (model input confidentiality) — cifrar y controlar el acceso a los inputs en tránsito y en reposo.

    2.6. Filtración y manipulación de datos de contexto

    Los datos de contexto son activos sensibles: pueden contener secretos corporativos, datos de clientes, o documentos confidenciales.

    Existen dos amenazas:

    Filtración: El repositorio es accedido de forma no autorizada, exponiendo su contenido directamente.

    Manipulación: Un atacante modifica el contenido del repositorio. Cuando el modelo procesa esos datos, actúa según las instrucciones maliciosas insertadas.

    Controles: - Confidencialidad de los datos de contexto (augmentation data confidentiality) - Integridad de los datos de contexto (augmentation data integrity)

    3. Controles generales

    Los controles generales aplican a todas las amenazas — de uso, de desarrollo y de runtime. Se organizan en tres grupos.

    3.1. Gobierno (Governance)

    El gobierno de la seguridad en IA implica establecer responsabilidades claras, mantener visibilidad sobre qué sistemas de IA existen y cómo operan, y asegurar el cumplimiento normativo.

    Controles clave: - AI program (#AI PROGRAM): incluye inventario de iniciativas de IA, análisis de impacto, asignación de responsabilidades y gestión de riesgos. - Security program (#SEC PROGRAM): incluye el ciclo de vida completo de la IA y sus activos específicos: datos de entrenamiento, parámetros, augmentation data, inputs, outputs. - Secure development program (#SEC DEV PROGRAM): tener procesos de desarrollo seguro que incorporen las particularidades de IA — data engineering, model engineering, data scientists — como parte integral del programa de desarrollo existente. - Development program (#DEV PROGRAM): ciclo de vida de desarrollo que incluya las actividades específicas de IA. - Compliance checking (#CHECK COMPLIANCE): verificar el cumplimiento de regulaciones y estándares aplicables (EU AI Act, ISO 42001, ISO 27001, entre otros). - Education (#SEC EDUCATE): capacitar a ingenieros, data scientists y equipos de seguridad en las amenazas y controles específicos de IA.

    3.2. Limitación de datos sensibles

    Los ataques a la confidencialidad e integridad se pueden reducir minimizando la superficie de datos: usar la menor cantidad y variedad de datos posible, y conservarlos el menor tiempo necesario.

    Minimización de datos (#DATA MINIMIZE): remover campos no necesarios de los datasets para prevenir filtraciones o manipulaciones. Limpiar datos de propósitos experimentales.

    Datos permitidos (#ALLOWED DATA): definir y controlar qué tipos de datos pueden usarse para entrenar o enriquecer el modelo.

    Retención corta (#SHORT RETAIN): eliminar o anonimizar datos una vez que ya no sean necesarios, o cuando la ley lo requiera. Minimiza el impacto si los datos son comprometidos.

    Ofuscación de datos de entrenamiento (#OBFUSCATE TRAINING DATA): proteger los datos de entrenamiento de manera que no sea posible re-identificar individuos a partir de ellos.

    Técnicas: - Enmascaramiento: reemplazar datos sensibles por alternativas que retienen la información necesaria (tokenización, perturbación, generalización) - Cifrado - Anonimización: reemplazar datos sensibles por etiquetas genéricas o pseudónimos - Privacidad diferencial: framework estadístico que garantiza que el modelo aprenda del conjunto como un todo y no de datos individuales, agregando ruido aleatorio para que no sea posible inferir individuos a partir del output

    Discreción (#DISCRETE): reducir la información técnica disponible para los atacantes. Minimizar los detalles técnicos expuestos en outputs del modelo y en documentación pública. Requiere equilibrar con la necesidad de transparencia.

    3.3. Limitación de comportamiento no deseado

    Un comportamiento no deseado en un modelo no siempre es resultado de un ataque: puede surgir de datos de entrenamiento insuficientes o incorrectos, un modelo desactualizado, errores en la ingeniería de datos. Los controles para estos casos apuntan a detectar y limitar ese comportamiento independientemente de su causa.

    Vigilancia (#OVERSIGHT): supervisión por parte de un humano o de lógica de negocio (guardrails) para detectar, corregir o detener decisiones del modelo antes de que tengan efecto.

    Ejemplos: - Lógica que impide que el baúl de un auto se abra mientras está en movimiento, incluso si el conductor parece solicitarlo - Solicitar confirmación del usuario antes de que un agente envíe correos masivos - Censura de outputs violentos o no éticos

    Limitaciones: las reglas muchas veces no se adaptan 100% a lo que se necesita. La supervisión humana es más costosa pero permite validación con más criterio.

    Mínimos privilegios (#LEAST MODEL PRIVILEGE): - Reducir las acciones del modelo a las estrictamente necesarias - Ejecutar acciones con los privilegios apropiados (el modelo hereda los privilegios del usuario que lo invoca, no los del sistema) - Evitar implementar autorización basada en instrucciones de IA o prompts, que son susceptibles a alucinaciones y manipulaciones

    Transparencia (#AI TRANSPARENCY): poder explicar de manera clara al usuario final el funcionamiento del modelo, su proceso de entrenamiento y la exactitud de sus resultados. Implica documentar abiertamente el ciclo de vida del modelo, detallando las fuentes de datos utilizadas, la arquitectura de los algoritmos, el entrenamiento previo, las limitaciones conocidas y los posibles sesgos. Busca responder al qué y cómo se construyó el sistema.

    Validación continua (#CONTINUOUS VALIDATION): testear el comportamiento del modelo contra un set de datos de test para detectar cambios, ataques permanentes (como envenenamientos), problemas de robustez (como ataques de evasión), fallas del sistema o degradación de performance.

    Explicabilidad (#EXPLAINABILITY): compartir información sobre cómo el modelo llegó a un resultado específico. Permite a los usuarios validar la exactitud, detectar comportamientos anómalos y entender qué cambiar para obtener un output diferente. Complementa con la transparencia.

    Model alignment (#MODEL ALIGNMENT): asegurar que el modelo se comporta de acuerdo con los valores e intenciones de sus creadores, incluso frente a inputs inesperados o adversariales.

    Testing de sesgo no deseado (#UNWANTED BIAS TESTING): detectar sistemáticamente si el modelo trata de manera desigual a distintos grupos. Los sesgos detectados pueden también revelar ataques de data poisoning: si alguien inyectó datos maliciosos para sesgar el modelo hacia ciertos grupos, el testing de sesgo puede descubrirlo.
